# Neo-Light Fork Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Split the single `neo-light` repo into two independent user repos (`warpuppy/neo-light`, `phantom/neo-light`) with a shared core submodule (`warpuppy/neo-light-core`), each with independent TOS configs, launch scripts, CI/CD, and learning logs.

**Architecture:** 3-repo structure with git submodules. Shared core contains all routing/BOA/dashboard logic. User repos contain only config overrides, launch scripts, and CI/CD. The `config_user.py` pattern allows per-user config without forking core logic.

**Tech Stack:** Python 3.10+, Git submodules, GitHub Actions, FastAPI, pytest, Hermes Agent

## Risks, Tradeoffs, and Open Questions

### Risks

| Risk | Mitigation |
|------|------------|
| Submodule drift (users on different core versions) | CI fails if submodule not at tagged release; docs: "always pin tags" |
| Config override conflicts | `config_user.py` pattern isolates changes; core `config.py` never edited in user repos |
| Secret leakage | `.env` in `.gitignore`; keys loaded from `~/.config/` at runtime |
| Phantom no T1 breaks router logic | Router already handles `T1.enabled=False` → skips T1; test in CI |
| BOA governance logs in different locations | Each repo has own `work/boa/governance/` — acceptable for isolation |
| Git submodule complexity | Document clearly; provide update script |

### Tradeoffs

| Tradeoff | Decision | Rationale |
|----------|----------|-----------|
| 3 repos vs 2 repos | 3 repos (core + 2 users) | Total isolation; shared logic in one place |
| Git submodules vs package | Submodules | User repos pin to specific core commits; no PyPI publishing needed |
| Config profiles vs branches | Config profiles (`config_user.py`) | Same logic, different values; no merge conflicts |
| Separate learning logs | Independent per user | Isolation; no cross-contamination |
| CI/CD per repo | Yes | Independent testing; no shared state |

### Open Questions

1. **Should phantom have access to warpuppy/neo-light-core?** Yes — she needs to update her submodule when core changes.
2. **Should there be a shared dashboard?** No — each user has their own; can be added later if needed.
3. **How to handle core updates?** PR workflow: edit core → PR → merge → tag → user repos update submodule.
4. **Should we use GitHub Actions or self-hosted CI?** GitHub Actions (free tier) — sufficient for now.
5. **How to handle secrets in CI?** GitHub Actions secrets per repo; never commit `.env`.
